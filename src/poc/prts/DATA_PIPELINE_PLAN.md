# PRTS 剧情引擎 V2 - 数据资产爬虫与语义提取规划

## 一、今日重大核心发现总结

1. **巨型静态资产字典机制**
   原版模拟器并未采用动态 API 加载，而是将包含万余张立绘、背景、音频的巨型索引树直接硬编码在了 HTML 的隐蔽 `<pre>` 标签（如 `#datas_char`、`#datas_link`）中。这为我们提供了现成且绝对完整的官方素材数据库。
   
2. **立绘语法的解构 (`#` 与 `$`)**
   剧情文本中对立绘的调用指令（如 `avg_npc_2231_1#1$1`）有着严格的层级逻辑：
   - `avg_npc_2231_1`：角色的基础骨架 Base ID（对应字典表）。
   - `$`：代表角色的大形态差分（Skin / Variant），通常表示换装（例如穿脱大衣、手持武器）。
   - `#`：代表当前大形态下，面部表情切片的数组索引（Expression）。

3. **通过剧本上下文自动反推角色真实身份**
   因为立绘入场指令 `[charslot(focus="m")]` 和发言指令 `[name="罗素"]` 在文本上紧密相连，我们完全可以通过扫描这种上下文关联，自动地把无名代号（如 `avg_npc_210_1`）和剧本里的自然语言名字（如“罗素”、“斯韦特兰纳”）绑定在一起，从而进行全自动的语义标注。

## 二、全站剧情资产爬虫实施方案 (Spider Action Plan)

利用现有的数据作为指引，编写批量 Node.js 爬虫，将《明日方舟》从开服至今的所有剧情全部扫描并转化为供 AI 消费的富上下文 JSON 库。

### 1. 爬取目标引路：`datas_override.txt`
`datas_override.txt` 包含了全站大量的剧情 ID 覆盖记录（如 `title:17-2_救赎迟来/BEG=17-2 救赎迟来 行动前`）。
- **流程**：读取 `datas_override.txt` 里的 `title:` 字段，提取出类似 `17-2_救赎迟来/BEG` 的剧情坐标，拼接为完整的访问 URL (`https://prts.wiki/w/...`)。
- **补充**：如果覆盖表不够全，可以利用 PRTS 网站的 Category API 调取所有带有 `[分类:剧情]` 标签的页面。

### 2. 下载与清洗引擎
- 通过 axios/fetch 请求网页 HTML，解析其 `<pre id="datas_txt">` 中的文本内容。
- 用正则表达式过滤出：
  - 所有的 `[character/charslot]` 及后续跟随的 `[name="..."]`。
  - 所有的 `[background]`、`[playmusic]`、`[playsound]`。
- **排雷须知**：脚本需要在两次请求间增加延迟以避免触发 Wiki 服务器的 Rate Limit (429) 或封禁。

## 三、产出物定义与规范 (Data Fusion Targets)

在扫描了数百集剧情文本后，将产出的数据与现在的 `datas_link.json` 和 `datas_audio.json` 进行融合，生成三个全新的增强版索引文件。

### 1. 增强型角色链路表 (`enhanced_link.json`)
以角色 `Base ID` 为主键，重塑 `datas_link.json`。
**数据结构规范要求**：
- **`render_data` (渲染锚点)**：完整保留原表的 `pos` (坐标偏移) 和 `size` (分辨率大小)。**这是极其致命的物理参数**，直接决定了引擎中该角色立绘的真实缩放比例、对齐方式和地平线高度，这省去了我们手动微调一万多张图片的恐怖工作量！
- **`names`**：汇总在所有剧情中被关联推测出的名字。须编写去重逻辑（忽略 `???`、合并同类项）。
- **`appeared_in`**：记录该角色登场过的所有剧情 ID。
- **`skins` / `expressions`**：将原本扁平的数组，按 `$`（形态）和 `#`（表情）拆解成树状结构。
- **`dialogues`**：在此表情下，收集最具代表性的 10 句对话文本（为后续 AI 标注提供语料）。
- **注意容错**：早期剧情或重要主角往往直接写名字或 Base ID，没有 `#` 和 `$`，此类情况需归集到 `default_expressions`。

**JSON 结构示意**：
```json
{
  "avg_npc_2231_1": {
    "names": ["斯韦特兰纳", "威严的军人"],
    "appeared_in": ["17-2_救赎迟来/BEG", "17-3_..."],
    "render_data": {
      "pos": { "x": -120, "y": 130 },
      "size": { "x": 1100, "y": 1100 }
    },
    "skins": {
      "$1": {
        "expressions": {
          "#1": { "dialogues": ["玩够了就把刀放下", "这是为了你的安全"] },
          "#8": { "dialogues": ["收回它！", "我以总司令的名义起誓！"] }
        }
      }
    }
  }
}
```

### 2. 音频情绪场景表 (`enhanced_audio.json`)
`datas_audio.json` 只有约 2690 条数据，说明音频是高度复用的通用资源。
- **真实 URL 拼接溯源**：原网页没有直接写明链接，在 V1 引擎 `krliov.toolbox.js` 中存在一段替换逻辑：如果以 `$` 开头，则去查字典，并且把 `sound_beta_2` 路径替换为 `torappu.prts.wiki/assets/audio/...mp3`。生成新表时应补全该真实链接。
- **使用频率与出现场景**：记录每首 BGM 或音效在哪些剧情中出现。频繁出现于“切尔诺伯格”、“塔露拉”场景的 BGM，后续可直接被 AI 打上“紧张/高压/宿命”的情绪标签。

### 3. 场景出场分布表 (`enhanced_backgrounds.json`)
背景图片的记录策略同理，记录其出现的全部剧情。后续甚至可以借用 GPT-4V 或直接靠剧情标题（如“龙门”、“荒野”）半自动为场景分类。

### 4. 高频公共音效与背景溯源
- 声效与背景图也必须遵循上文原则，在最终生成的 `enhanced` 表中添加 `appeared_in: []` 以标注出处的剧情关卡。
- 特别注意：音频文件（`datas_audio.json`）只有 2690 行，存在极高的跨关卡复用率，且其 JSON 值中往往没有真实链接。需要在处理该表时，结合 `krliov.toolbox.js` 和 `txt_analyze` 中的字符串拼接算法（如包含 `sound_beta_2` 关键字时的正则替换），将其还原为真实可下载的 CDN MP3 地址。

## 四、最终愿景 (End Game)
当这三个 `enhanced_xxx.json` 文件生成完毕后，我们就彻底完成了**对 PRTS 的“语义逆向”**。
我们直接把这些带对白、带场景分布的 JSON 切割成块送进大语言模型进行最后的“一键情绪打标”。
到了真正使用 Vue 3 制作 `<ArkVnPlayer>` 时，AI 编剧就能直接拿着带有人类自然语言标签（如 `{"name": "斯韦特兰纳", "emotion": "angry"}`）的数据字典，信手拈来地生成毫无渲染瑕疵的动态演出剧本！
