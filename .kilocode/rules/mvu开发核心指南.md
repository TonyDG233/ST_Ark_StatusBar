# MVU开发核心指南

本文档旨在全面、系统地阐述基于MVU（Magical Variable Update）框架进行角色卡开发的核心概念、流程与最佳实践。内容整合自项目内的多个规则文档及核心开发经验。

---

## 1. 核心概念：MVU是什么？

MVU变量框架是一个独立的酒馆助手脚本，其核心是通过AI的自然语言输出来驱动游戏状态（即“变量”）的变更。它使得角色卡能够拥有动态的、可记忆的状态，极大地丰富了互动体验。

其标准工作流如下：
1.  **定义结构**: 在 `schema.ts` 文件中使用 Zod 4.x 定义变量的完整结构、类型和约束。
2.  **初始化**: 在世界书条目 `[initvar]变量初始化勿开` 或开局消息的 `<initvar>` 块中设定变量的初始值。
3.  **提示AI**: 通过世界书中的三大核心提示词（变量列表、更新规则、输出格式），让AI理解变量的含义并学会如何更新它。
4.  **AI输出**: AI在回复中生成特定格式的 `<UpdateVariable>` 块，内含对变量的更新指令（JSON Patch）。
5.  **MVU解析**: MVU框架自动解析AI输出中的指令，并据此更新当前消息楼层的变量。
6.  **脚本/界面交互**: 前端界面和后台脚本可以读取、修改变量，或监听变量更新事件以触发复杂逻辑。

---

## 2. 第一步：变量结构设计 (`schema.ts`)

变量结构是整个MVU系统的基石，其设计的优劣直接决定了项目的稳定性和可维护性。

### 2.1 核心工具与原则

-   **核心库**: **Zod 4.x** 和 **lodash**。它们是全局可用的，无需在`schema.ts`中`import`。
-   **文件纯粹性**: `schema.ts` 文件**只应负责定义和导出 `Schema` 对象**，不应包含任何副作用代码，如调用 `registerMvuSchema`。注册操作应在专门的脚本中进行（如`角色卡/脚本/变量结构/index.ts`）。
-   **幂等性**: Zod的`transform`必须是幂等的，即 `Schema.parse(Schema.parse(input))` 的结果应与 `Schema.parse(input)` 完全相同，以保证增量更新的稳定性。
-   **类型建议**:
    -   数值：优先使用 `z.coerce.number()` 而非 `z.number()`，以增强容错性。
    -   数据结构：优先使用 `z.record(z.string(), ...)` 的对象结构，而非 `z.array(...)`，因为具名键比数组索引更易于AI理解和维护。
-   **默认值**: 优先使用 `z.prefault` 而非 `z.default`。对于复杂的对象，应为每个字段乃至整个对象提供默认值（如 `.prefault({})`），以确保AI在增量添加数据时结构的完整性。

### 2.2 特殊变量前缀

为精细化控制变量的行为，MVU支持两种特殊前缀：

-   `_` **(下划线)**: **AI只读**。AI可以在“变量列表”中看到此变量的值，但在其输出的 `<UpdateVariable>` 块中无法修改它。适用于需要展示给AI但由系统或脚本控制的内部状态。
-   `$` **(美元符)**: **AI不可见**。此变量不会通过 `{{format_message_variable::stat_data}}` 宏展示给AI，AI自然也无法直接更新它。适用于纯粹由脚本/前端界面使用的、无需AI感知的内部变量。

## 3. 第二步：变量初始化

变量的初始状态决定了故事的开端。

-   **全量方案 (适用于新聊天)**:
    1.  在世界书条目 `[initvar]变量初始化勿开` 中定义一套完整的、默认的变量初始值（YAML格式）。
    2.  在每个开局剧情（第0楼）的开头，使用 `<initvar>...</initvar>` 块来**覆盖**默认值，实现不同开局的独特设定。
-   **增量方案 (适用于微调)**: 如果不同开局的变量差异很小，可以在开局剧情的**末尾**直接插入一个 `<UpdateVariable>` 块。这会像AI回复一样，对 `[initvar]` 提供的基础值进行一次局部修改，避免了重复定义整个变量结构。

---

## 4. 第三步：让AI理解变量 (世界书提示词)

这是连接AI思维与变量系统的桥梁，由三个核心的世界书条目组成。

### 4.1 `变量列表`

-   **作用**: 告诉AI变量的**当前值**及其**业务含义**。
-   **核心实现**: 使用酒馆助手宏 `{{format_message_variable::stat_data}}` 将最新的变量状态（JSON格式）动态注入到提示词中。也可以使用更具体的路径，如 `{{format_message_variable::stat_data.角色.白娅.依存度}}`。
-   **关键要点**:
    -   **插入位置**: 必须放在 **D1** (上一次AI回复之后) 或 **D0** (本次用户输入之后) 的位置。这能让AI确信它看到的是紧随最新剧情的变量状态，而不是过时的信息。
    -   **解释含义**: 对于非自明性的变量（如“依存度”），需要额外提供文本描述（或通过后续的EJS动态提示词）来解释不同数值区间的具体意义，即“分段好感度”逻辑。

### 4.2 `[mvu_update]变量更新规则`

-   **作用**: 向AI提供更新变量的**指导方针**和**约束条件**。
-   **核心结构**:
    -   沿用`schema.ts`的层级结构，让AI易于关联。
    -   使用 `type`, `range`, `format` 字段来提示AI期望的值类型。
    -   **`check` 字段是核心**，用自然语言描述更新变量应遵循的逻辑和情境。
-   **最佳实践**:
    -   **合并同类**: 将更新逻辑相似的变量合并，如 `主角.能力面板.${六维}`。
    -   **保持简洁**: 省略那些变量名已足够清晰的规则。
    -   **插入位置**: 可以放在角色定义之后、D4等注意力权重较低的位置，因为其核心内容（`check`）会被“变量输出格式”中的思维链“召回”。

### 4.3 `[mvu_update]变量输出格式`

-   **作用**: **强制规定**AI更新变量时必须采用的输出结构。
-   **核心格式**:
    ```
    <UpdateVariable>
      <Analysis>...</Analysis>
      <JSONPatch>[...]</JSONPatch>
    </UpdateVariable>
    ```
-   **`<Analysis>` (思维链/CoT)**:
    -   这是至关重要的一环。它强制AI在执行更新前，先进行逻辑分析，并**“回忆”和复述`变量更新规则`中的`check`要点**。这极大地提高了变量更新的准确性和稳定性。
-   **`<JSONPatch>` (更新命令)**:
    -   AI将分析结果转化为具体的更新指令，如 `replace`, `delta`, `insert`, `remove` 等。MVU框架会直接解析这部分内容来修改变量。

### 4.4 适配双更新模式

为了兼容不同的用户配置，条目前缀 `[mvu_update]` 和 `[mvu_plot]` 用于区分提示词的用途：
-   `[mvu_update]`：只发送给负责**更新变量**的AI模型。
-   `[mvu_plot]`：只发送给负责**生成剧情**的AI模型。
-   无前缀：同时发送给两个模型。
因此，`变量更新规则`和`变量输出格式`必须添加`[mvu_update]`前缀。

## 5. 第四步：处理AI的变量更新输出

-   **酒馆正则**:
    -   **目的**: 避免已执行过的 `<UpdateVariable>` 块在后续对话中被重复发送给AI。这可以节省Token，减少AI的注意力分散，并防止AI“偷懒”照抄旧的更新指令。
    -   **核心正则**: `[不发送]去除变量更新`，它利用“仅格式提示词”功能，在发送给AI时将 `<UpdateVariable>...</UpdateVariable>` 块替换为空字符串。
    -   **深度控制**: 可以设置正则的“最小深度”，例如设为4，则只会移除倒数第5楼及更早的更新块，保留最近的更新记录以供AI参考。

---

## 6. 第五步：动态化与自动化 (脚本与EJS)

当静态的变量和提示词无法满足复杂需求时，就需要代码介入。

### 6.1 提示词模板 (EJS)

-   **目的**: 根据**当前变量值**，动态地、条件性地生成和发送提示词。
-   **核心语法**:
    -   `<%_ ... _%>`: 执行不产生输出的JS代码（如 `if/else` 逻辑）。
    -   `<%= ... %>`: 将表达式的结果直接输出到提示词中（类似宏）。
    -   `print('...')`: 在代码块内输出提示词文本。
-   **核心函数**:
    -   `getvar('stat_data.路径', { defaults: ... })`: 获取变量值，并可提供默认值。
    -   `matchChatMessages(['关键字'])`: 检查最近的聊天记录是否包含特定词汇，用于模拟绿灯。
    -   `await getwi('条目名')`: 获取并输出另一个世界书条目的内容。
-   **激活绿灯**: 在条目开头添加 `@@preprocessing`，可以让提示词模板在酒馆激活世界书**之前**就完成渲染，从而使动态生成的内容能够被绿灯系统正确识别。

### 6.2 酒馆助手脚本 (`.ts`)

-   **应用场景**: 需要与酒馆进行复杂交互、对比新旧变量、或实现自定义UI时。
-   **初始化**: 任何与MVU交互的脚本，都必须在开头执行 `await waitGlobalInitialized('Mvu');`。
-   **通过监听MVU事件进行扩展**:
    -   `Mvu.events.COMMAND_PARSED`: 在更新命令被**解析后、执行前**触发。是进行指令修复（如简繁转换、修复AI格式错误）的最佳时机。
    -   `Mvu.events.VARIABLE_UPDATE_ENDED`: 在变量**更新完毕后**触发，并同时提供 `new_variables` 和 `old_variables`。这是脚本扩展的核心，可用于：
        -   实现比Zod更复杂的校验（如比较新旧值）。
        -   触发游戏事件（如 `toastr.success('好感度突破！')`）。
        -   基于变量变化，调用 `injectPrompts` 来动态管理用于激活绿灯的隐藏提示词。
-   **主动操作MVU**:
    -   `Mvu.getMvuData({ type: 'message', message_id: ... })`: 读取任意楼层的MVU变量。
    -   `Mvu.replaceMvuData(newData, { ... })`: 强制覆写MVU变量。
    -   `Mvu.parseMessage(content, old_data)`: 在`generate`回调等非标准流程中，手动触发对AI生成文本的解析。
-   **与前端UI结合**:
    -   `defineMvuDataStore` (`src/util/mvu.ts`): 这是一个预设的辅助函数，用于在Vue/Pinia组件中创建响应式的store，轻松实现UI与MVU变量的双向绑定。

## 7. 附录：调试与最佳实践

-   **EJS调试**: 使用 `alert()` 或 `toastr.info()` 在模板执行时弹窗显示变量值；或使用 `<%_ debugger; _%>` 配合浏览器开发者工具进行断点调试。
-   **变量调试**: 在酒馆助手中开启“变量更新出错时通知”；使用“变量管理器”实时查看各楼层的变量状态。
-   **健壮性设计**:
    -   在 `schema.ts` 中，为可能在游戏中途新增的、非必需的变量（如新角色）设置 `.prefault('待初始化')`，防止AI因遗漏部分字段而导致整个对象创建失败。
    -   在EJS中，使用 `getvar('path', { defaults: ... })` 来安全地访问可能尚不存在的变量。
