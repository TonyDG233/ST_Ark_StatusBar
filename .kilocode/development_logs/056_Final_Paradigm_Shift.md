# 056_为何“标准答案”害了你：文档的陷阱 (Why the "Standard Answer" Failed You)

**日期**: 2026-01-29
**状态**: **终极复盘**
**背景**: 您指出 Phase 3 的开发是严格遵循 MVU/酒馆助手官方文档（`后台控制和利用变量`）进行的，但结果依然崩坏。

---

## 1. 您没有做错，是“示例”误导了“架构”

我仔细重读了您提供的文档。您说得对：
*   文档确实推荐用 `VARIABLE_UPDATE_ENDED` 来“限制数值”、“触发弹窗”、“强制修改”。
*   文档确实推荐用 `injectPrompts` 来“动态注入”。
*   文档确实推荐用脚本来“解析消息”。

**您严格执行了这些“最佳实践”。** 甚至 `unified_script.js` 也是这一思路的集大成者（试图在一个脚本里控制一切）。

**那为什么会崩？**
因为文档里的例子是**原子级 (Atomic)** 的：
*   *“限制好感度在0-100”* —— 这是一个瞬间动作，改完就结束，没有后续。
*   *“修复繁体字”* —— 这是一个瞬间动作，改完就结束。

但您在 Phase 3 构建的是**事务级 (Transactional)** 的：
*   *“检测新角色 -> 推送初始化任务 -> 等待LLM回复 -> 再次检测 -> 清理任务”*
这是一个**跨越时间、跨越多次交互**的长链条逻辑。

**核心结论**：酒馆助手的事件系统 (`Mvu.events`) 只能支撑**瞬间的、无状态的修正**。一旦您试图在里面跑**有状态的、多步骤的流程控制 (Flow Control)**，由于 LLM 的不可控和酒馆事件的不稳定，链条必然断裂。

---

## 2. 真正的范式：原子化后端 + 提示词流程

您问“大型项目的范式是什么”。
在 LLM 应用开发中，范式是：**Code 管瞬间，Prompt 管流程**。

### 错误范式 (Phase 3 & Unified Script)
试图用代码管流程：
*   代码：`if (task_queue.has('init')) { ... }` (代码试图理解剧情进度)
*   代码：`pushTask(...)` (代码试图调度 LLM)
*   **结果**：代码和 LLM 不同步，死锁，风暴。

### 正确范式 (Surviving the Chaos)
1.  **后端脚本 (Code)**: 只做**刹车**和**仪表盘**。
    *   *仪表盘*: 把 `time` 格式化成 `YYYY-MM-DD` 给 UI 看。（原子操作，安全）
    *   *刹车*: `stat_data.hp` 变成 -10 了？强制改成 0。（原子操作，安全）
    *   **决不做方向盘**：不要试图指挥 LLM “现在该干嘛”。

2.  **提示词 (Prompt)**: 做**方向盘**。
    *   在 EJS 里写：`<% if (stat_data.hp <= 0) { %> [系统指令：你已重伤倒地，请描述濒死体验] <% } %>`
    *   让 Prompt 直接根据当前状态（State）驱动 LLM，而不是靠后端推任务（Event）。

## 3. 对您的回答：现在该做什么？

您已经累了。不要再重构架构了。
您手里的 `unified_script.js` 虽然逻辑复杂，但它至少是一个**已经写好**的单体。

**最后一步建议**：
1.  **保留** `unified_script.js` 作为核心。
2.  **阉割** 其中的“流程控制”逻辑（比如自动检测新角色并自动初始化的逻辑）。把这些容易出 Bug 的“自动化”砍掉。
3.  **保留** 其中的“原子操作”逻辑（比如 UI 渲染、数据读取）。
4.  **手动化**: 遇到需要初始化、需要总结的时候，不要让脚本自动跑。在 UI 上加个按钮，手动触发。
