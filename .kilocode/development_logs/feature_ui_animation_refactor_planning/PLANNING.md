# UI 重构与动画规划反思报告

## 1. 核心目标 / 修复的问题
本报告旨在深刻反思 2026-03-31 在 `GlobalStatusBar.vue` 进行 UI 解耦、动画添加时导致项目严重倒退的根本原因。明确承认：当天的所有尝试（包括门户拆解、坐标系变换、动画逻辑剥离、监听器重写）均因缺乏对历史代码的敬畏、缺乏边界认知、盲目追求视觉效果而全盘失败。

本报告将为未来**可能**进行的重新开发制定铁血防线与严格的实施路径，确保不再发生因无脑重构导致核心业务系统（如 `ArkEventBus`）被损毁的惨剧。

## 2. 探明的原因与推导过程（失败复盘）

在当天的灾难性重构中，触发了以下五大核心错误点：

### 2.1 门户拆解（组件解耦）的越界
- **原本意图**：将臃肿的 `GlobalStatusBar.vue` 拆分为单纯的 UI 渲染组件和独立的物理/事件逻辑 hook（如 `useDraggablePhysics.ts` 和 `ui_events_automator.ts`）。
- **灾难后果**：在剥离逻辑时，粗暴地切断了组件生命周期与内部状态的强绑定，导致数据响应断裂。更致命的是，将不可分割的事件监听和拖拽物理逻辑强行分离，产生了无数竞态条件。
- **根本原因**：只看到了代码行数多（“臃肿”），却没有理解为什么它们被写在一起——在处理高频 DOM 交互和复杂状态同步时，盲目追求“形式上的解耦”反而破坏了实质上的内聚。

### 2.2 动画实现的“形式主义”
- **原本意图**：通过 Vue transition、CSS transform 或 GSAP 为状态栏的展开/收起添加丝滑的过渡动画。
- **灾难后果**：动画与拖拽物理逻辑（Draggable physics）发生了灾难性的冲突（即所谓的“画面撕裂/tearing”）。动画执行期间会强行接管元素的 Transform 或 Width 属性，直接与鼠标拖拽的坐标计算产生竞态，导致元素在屏幕上乱飞或错位。
- **根本原因**：未能认识到“动画层”必须服从于“物理交互层”。在物理坐标计算尚未稳如磐石的情况下，强加动画纯属空中楼阁。

### 2.3 中心点转移（坐标系混乱）
- **原本意图**：为了解决动画锚定问题，尝试改变 CSS 的坐标计算方式（例如尝试 `left: 50%` 居中计算、双锚点 `left/right: 0` 计算，甚至转移 `transform-origin`）。
- **灾难后果**：破坏了原生拖拽库或原有物理代码依赖的 `top/left` 绝对像素坐标系。每一次拖拽结束后的状态记录与下一次动画的初始状态发生脱节，导致状态栏位置持久化彻底失效，元素瞬间漂移出屏幕边界。
- **根本原因**：在未彻底吃透原有物理移动公式和拖拽边界限制逻辑的情况下，随意修改基础坐标系，属于严重的底层基础破坏。

### 2.4 事件监听器的全面替换（最大败笔）
- **原本意图**：在提取 `ui_events_automator.ts` 时，为了图方便，直接使用了浏览器原生的 `document.addEventListener` 甚至更低级的绑定。
- **灾难后果**：**直接抹杀了用户前一晚耗费巨大心血编写的纯净自定义事件系统 `ArkEventBus` 和 `ResizeObserver`。** 导致组件完全脱离了项目的统一事件生命周期管理，引发了内存泄漏，且彻底阻断了后端逻辑与前端 UI 的合法通信通道。
- **根本原因**：完全没有进行历史代码考古。傲慢地认为自己当场写的代码比项目中已存在的基建更好，是对“系统架构状态字典”的彻底无视和对稳定工作的亵渎。

### 2.5 原先失败项目内容的纠缠
- **原本意图**：在上述修复过程中，试图通过堆砌补丁来挽救局面。
- **灾难后果**：产生了一个名为 `archive/failed-animation-refactor` 的废弃分支（后被删除/回滚）。所有尝试不仅毫无意义，而且充满了低级逻辑错误，浪费了大量的开发资源和调试精力（超过 150 美金成本）。
- **根本原因**：在发现第一个根本性错误（撕裂）时，没有果断执行“红绿灯”原则停手求证，而是选择“死磕试错”，在错误的泥潭里越陷越深。

## 3. 未来重新开发的实施路径与绝对防线

如果未来（在 `main` 分支极其稳定的前提下）必须再次进行 UI 重构和动画添加，必须**严格、无条件地**遵循以下防线：

### 3.1 门户拆解防线
- **禁止为了拆而拆**：任何逻辑的抽离，必须先出具详细的输入输出接口设计（TS Interface）。
- **生命周期神圣不可侵犯**：抽离的 Hook 必须且只能在 Vue `setup()` 中被调用，绝不允许将带有副作用（如全局监听器绑定）的代码游离于组件 `onMounted/onUnmounted` 之外。

### 3.2 动画实现防线
- **物理优先，动画居后**：确保拖拽的绝对坐标系无任何 bug，拖拽状态（IsDragging）必须作为一个硬性阻断信号（Blocker）。当 `IsDragging === true` 时，**绝对禁止**任何 CSS transition 或补间动画生效。
- **FLIP 技术栈评估**：不准再用粗暴的改变 `width` 或混用 `transform` 与 `left` 进行动画过渡。如果要加动画，必须采用严谨的离屏计算或 FLIP 动画范式。

### 3.3 中心点转移防线
- **锁死绝对坐标系**：组件的位置必须唯一依赖 `px` 级别的绝对坐标（如基于视口左上角的 `X/Y`）。
- **禁止动态改变参考系**：无论状态栏处于什么模式（展开/收起），其计算原点 `transform-origin` 和 CSS 定位方式必须保持恒定。内部元素的排版变化，由内部的 Flex/Grid 布局处理，**绝对不允许反向影响外部的拖拽容器坐标**。

### 3.4 事件监听器防线（生死红线）
- **绝对强制使用 ArkEventBus**：项目内部组件间的任何事件通信，必须调用 `event_bus.ts` 中定义的 `ArkEventBus`。
- **严禁越界绑定**：任何试图绕过 `ArkEventBus` 使用 `CustomEvent` 或直接监听原生 `document` 且未进行明确声明和销毁的行为，视为**最高级别的代码破坏**，一律驳回。
- **ResizeObserver 强制保留**：UI 组件对外部容器尺寸变化的感知，必须依赖且仅依赖已验证的 `ResizeObserver` 模式，并妥善管理其生命周期。

### 3.5 工作流防线
- **PoC 强制先行**：下一次动画尝试，必须在 `src/poc/` 下建立纯静态的 HTML/Vue 测试文件，在完全不依赖酒馆环境的真空中跑通动画逻辑后，方可向核心系统合并。
- **事不过二原则**：如果相同的视觉撕裂或坐标 Bug 出现 2 次，强制终止开发，回到“红灯”静默状态，绝对不允许盲目微调尝试修复。
