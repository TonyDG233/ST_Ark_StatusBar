# 重构反思与破局计划：夺回代码的控制权

**日期：** 2026-04-13
**背景：** 这不是一份普通的规划，而是一次深刻的复盘。长达一个月的原地打滚、反复重构却不见成效、修一个 Bug 出两个 Bug，这并不是因为项目体量有多大（仅仅不到 4000 行），而是因为**失控**。

---

## 1. 为什么会变成这样？（病因诊断）

你之所以会觉得“完全看不懂自己一手搓出来的项目”，是因为项目被 AI 裹挟进了一个极其危险的陷阱：**伪设计模式与职责粉碎**。

1. **盲目套用“最佳实践”导致的碎片化：**
   - AI 在处理重构时，很喜欢套用各种高大上的名词（比如 Facade、Adapter、EventBus）。结果呢？为了所谓的“解耦”，它把本来在一块儿的代码硬生生撕碎了。
   - 例如 `statusbar_manager.ts`：你说“把复杂逻辑移出去”，它就把纯逻辑代码切到了 `worldbook_automator.ts`，却把触发这些逻辑的“发令枪（事件监听器）”还留在了 `Manager` 里。这种“身首异处”的做法，让你在查 Bug 时，永远不知道子弹是在哪里射出去的，又是在哪里命中的。
2. **事件驱动（Event-Driven）滥用造成的“隐性逻辑链路”：**
   - 项目里到处都是 `eventOn` 和 `dispatchEvent`。事件驱动的好处是解耦，但巨大的代价是**控制流丧失**。
   - 当你想找“拦截服务是怎么启动的”，你找不到一条自上而下的直线调用链。因为它是通过某个角落抛出的某个事件，“碰巧”在另一个角落被接住然后启动的。一旦某个事件因为酒馆底层变动而没触发（或者晚触发了 10ms），整个系统就像多米诺骨牌一样悄无声息地死掉。没有任何日志，没有任何调用栈，你当然无法调试。
3. **黑盒宿主（SillyTavern）带来的变数叠加：**
   - 在我们不完全掌控底层的环境中，AI 还试图写一层极其复杂的抽象。这就像在流沙上建高楼，一点点微调都会让整套看似完美的抽象崩溃。

**结论**：你并没有做错什么，软件开发也不应该这么痛苦。痛苦的根源在于：**我们在用一套极其复杂、隐晦的“企业级分布事件架构”，去管理一个仅仅 4000 行的、寄生于不稳定宿主的单体插件。**

---

## 2. 破局之道：回归“显性直白”的编程模式

要夺回控制权，让代码重新变得“你能看懂且能修改”，我们必须摒弃花里胡哨的解耦，回归最古老、也最有效的编程方式：**显性的、串行的、可追踪的指令式调用链。**

### 2.1. 建立极其直白的“主板”（The Mainboard Entry）
我们将彻底改造 `index.ts`（或者新建一个 `bootstrap.ts`）。它将成为整个插件**唯一**的宏观入口，就像电脑的主板一样清晰：

```typescript
// 纯伪代码演示未来清晰的结构
async function startPlugin() {
  try {
    log('1. 等待酒馆宿主核心数据就绪...');
    await checkHostReady(); 

    log('2. 加载基础配置...');
    const config = await ConfigStore.init();

    log('3. 挂载并初始化【世界书业务模块】...');
    // 初始化时传入 config，模块内部负责把自己的事情打理好
    await WorldbookModule.mount(config); 

    log('4. 启动【发送拦截服务】...');
    // 显式地按顺序启动！如果怀疑没启动，直接在这里 console.log
    await InterceptorService.startListening();

    log('5. 渲染前端 UI...');
    UIManager.mountGlobalUI();

    log('=> 插件完全就绪，启动成功！');
  } catch (err) {
    console.error('插件启动失败，卡在步骤: xxx', err);
    // 这里还能显式地执行回滚或重试逻辑
  }
}
```
**好处**：这 20 行代码，就是你这个插件的“生命周期总纲”。想延时加载？在 `log('4')` 前面加一句 `await sleep(500)`；怀疑拦截服务挂了？直接找到第 4 步看它有没有抛出错误。

### 2.2. 强制业务高内聚：把碎尸缝合起来
我们将废除现在 `statusbar_manager.ts` 那种“假门面真怪胎”的设计。

*   **业务结构组成模块**：例如“世界书系统”，它就应该是一个干净的文件夹 `worldbook/`。里面有一个明确的出口类 `WorldbookCore`。
*   **把监听器塞回它该在的地方**：如果世界书系统需要监听 `WORLDINFO_UPDATED` 才能刷新自己，那么这个监听代码就**老老实实写在 `WorldbookCore.init()` 里面**。当刚才的主板调用 `WorldbookModule.mount()` 时，它自然就被挂上了。不需要到处抛事件。
*   **如果出了 Bug，你就只去这个文件夹里找。** 不用再跨越 3 个文件去追一个莫须有的 Event。

### 2.3. 控制流的重夺：手动重载的可能
当管线变得显性后，想要实现“手动重载（Reload）”就变得轻而易举：

```typescript
async function reloadPlugin() {
  log('正在清理旧实例...');
  UIManager.unmountAll();
  InterceptorService.stopListening();
  WorldbookModule.destroy();
  
  log('重新执行启动管线...');
  await startPlugin();
}
```

## 3. 接下来怎么做？(Immediate Actions)

不要绝望。4000 行代码，对于重构来说，只要找对了骨架，最多需要一两天的“刮骨疗毒”。

1.  **停掉所有关于“事件注册表”、“统一监听网关”的乱七八糟的设计。**
2.  **第一步清算**：我们将直接分析 `index.ts` 和 `statusbar_manager.ts`，将所有乱放的 `eventOn`、`setInterval` 和初始化逻辑，重新整理成一条类似 2.1 节中那样**肉眼可读、从上到下的 `async main()` 启动链**。
3.  **第二步缝合**：将 `statusbar_manager.ts` 里那些残缺的监听器，塞回给它们对应的业务模块内部（比如归还给 `worldbook_automator.ts` 或者重新命名的核心业务类）。让 `manager` 回归到一个真正的简单工具类，而不是掌控生死的上帝。
