**日期：** 2026-04-09
**背景：** 针对“事件监听的边界”与“AI 协作下的技术选型宣导”进行的深度反思。

## 1. 局部事件的边界：原生 `CustomEvent` 强类型化的可行性

**用户的痛点提问**：
> 当一个监听器根本不跨越文件进行传递时，还需要强定义走我们自己的监听器（ArkEventBus）吗？能否用 `CustomEvent` 做强定义，一方面 AI 熟悉这种业界最常用的做法，能写对；另一方面能在开发时通过报错自行找回定义位置？

**系统的工程级反馈**：
**非常犀利且正确。** 这是在经历了重度工程化后的极佳反思。

*   **跨文件与局部事件的本质区别**：如果一个事件只在紧密耦合的组件内部（或极小范围内）流转，强行引入全局的 `ArkEventBus` 反而是“过度设计（Over-engineering）”。
*   **AI 的“默认寻路”习性**：大模型在训练时，阅读了上百亿行的开源代码，其中绝大多数 DOM 级别的事件通信都是用 `document.dispatchEvent(new CustomEvent(...))`。如果你强迫它用自己造的轮子 `ArkEventBus`，它极易因为短期记忆遗忘而产生幻觉，最后又退回到原生的写法。
*   **最优解（顺应 AI 的本能并加上枷锁）**：**完全可以，且应该对原生的 `CustomEvent` 进行强类型化。**
    在 TypeScript 中，我们可以通过 `declare global` 扩展 `DocumentEventMap`。
    ```typescript
    declare global {
      interface DocumentEventMap {
        'ark:internal-action': CustomEvent<{ actionType: string; payload: any }>;
      }
    }
    ```
    一旦这样定义，AI 就算按本能去写 `document.addEventListener('ark:internal-action', (e) => { ... })`，编译器也会自动推断出 `e.detail` 的类型。如果 AI 瞎写了一个未注册的事件名，TS 直接爆红报错。
    **这不仅降低了 AI 的出错率，还利用了它自身的纠错本能（看到报错去查类型文件）。**

## 2. 技术选型的文档缺失：为什么 AI 总是“忘带工具”？

**用户的痛点提问**：
> 开始那个商业项目的技术选型，当前我们自己技术选型表单就很粗糙，导致可能 AI 都不清楚我们自己有个事件总线，或者说提了一嘴后不清楚这玩意啥时候要用要怎么用。

**系统的工程级反馈**：
你彻底抓住了“为什么 AI 总是重构失败”的另一块拼图。

*   **缺失的地图**：当我们把一堆文件扔给 AI 时，AI 的视角就像是被空投进了一个陌生的城市。如果没有一张清晰的《技术选型与基础设施地图》，它遇到河流（组件通信）时，它的第一反应是自己砍树造船（写原生的 Event），而不是去寻找这座城市里早就建好的大桥（`ArkEventBus`）。
*   **商业项目的启示**：商业项目之所以稳，是因为它在开发前，有一份极其明确的清单：
    *   网络请求：用 `Axios`（不要用 `fetch`）
    *   状态管理：用 `Pinia`（不要传 `props`）
    *   **在我们的项目中，同样需要这样一份强力契约。**

### 改进方向：建立 `TECH_STACK.md` 或在规范中强化
我们需要在项目中以机器可读的方式，明确罗列：
1. **全局状态流转**：使用 `shared_ui_state.ts`。
2. **跨模块底层事件**：使用 `ArkEventBus`（并附上一行最简单的用法示例代码）。
3. **DOM 内局部/视图通信**：允许使用 Vue 的 `emit` 或强类型的 `CustomEvent`。
4. **CSS 动画**：禁止使用 JS 直接控制，必须通过切换 Vue 类名触发 CSS `transition`。

只有把这座城市的“基础设施地图”交到 AI 手里，它才不会在重构时疯狂地“重复造轮子”甚至“拆毁承重墙”。
