## 3. 探索过的方案路径与最终方案

### 3.1 角色静/动态区分机制的演进

*   **方案 A (Agent 最初的错误理解)**: 认为 `变量列表.ejs` 负责检查世界书并执行不同的渲染逻辑。**[已废弃]**
*   **方案 B (Agent 提出的重构方案)**: 废弃 `discriminatedUnion`，统一使用 `CharacterFullSchema`，通过 `_internal.static_profile_uid` 的**存在与否**作为唯一标识。 **[因流程违规被驳回]**
*   **方案 C (符合您最初设计的最终方案)**: 维持 `character.ts` Schema 中 `z.discriminatedUnion('has_static_profile', ...)` 的设计。
    *   **`has_static_profile` (boolean)**: 作为**数据结构**的判断依据。在角色首次初始化时，由后端脚本检查世界书后**一次性设定**。
    *   **`_internal.static_profile_uid` (number | optional)**: 作为**性能优化**的手段。如果 `has_static_profile` 为 `true`，则此字段**必须**存在，存储世界书条目的 `uid`，供动态注入时直接调用。

### 3.2 动态上下文注入机制的演进

*   **方案 A (Agent 最初的错误理解)**: 尝试从 EJS 中回调后端 TS 函数。 **[因技术不可行被驳回]**
*   **方案 B (最终方案 - Plan A)**: 由**后端 `global.ts`** 脚本作为总调度。
    *   **注入时机**: 监听 `CHAT_GENERATING` 事件。
    *   **注入执行**: 调用 `character.ts` 中的 `injectContextForPlotLLM` 函数。
    *   **注入逻辑**: 该函数读取 `_internal.static_profile_uid`，通过 `updateWorldEntry` API，使用**正则表达式**定位并**临时覆写**静态世界书条目。
    *   **清理时机**: 监听 `MESSAGE_RENDERED` 事件。
    *   **清理执行**: 调用 `character.ts` 中的 `cleanupInjectedContext` 函数，将世界书恢复原状。
*   **方案 C (最终方案 - Plan B / 备用)**:
    *   如果 Plan A 导致系统不稳定，则启用此方案。
    *   `injectContextForPlotLLM` 的逻辑变更为：更新一个**独立的、高优先级的世界书条目** `[mvu_plot]动态角色上下文` 的内容。
    *   `cleanupInjectedContext` 的逻辑变更为：清空该条目的内容。
