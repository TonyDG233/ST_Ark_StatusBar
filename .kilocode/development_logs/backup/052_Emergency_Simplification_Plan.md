# 052_紧急架构熔断与重构方案 (Emergency Simplification Plan)

**日期**: 2026-01-29
**状态**: **建议立即执行**
**背景**: 项目陷入复杂度泥潭，开发停滞，维护成本过高。EJS 与 TavernHelper 环境均不具备支撑当前精密架构的稳定性。

---

## 1. 核心诊断：哪怕代码是完美的，路也走不通

我们要承认一个残酷的现实：**SillyTavern 不是一个应用服务器，它只是一个聊天软件。**

我们之前的架构（Backend <-> Queue <-> EJS <-> LLM）试图在聊天软件里模拟一个**操作系统**的任务调度机制。这在技术上是可行的，但在**工程上是灾难性的**。
因为：
*   EJS 是渲染层，不该有逻辑。
*   Backend 是脚本层，控制不了 LLM 的时序。
*   LLM 是概率性的，不能当作 CPU 指令集用。

**结论**：必须立刻停止“自动化闭环”的幻想。

---

## 2. 救援方案：架构“脑叶切除” (Lobotomy Strategy)

我们需要把负责“思考”和“调度”的复杂逻辑全部砍掉，只保留最基础的“读写”功能。

### 2.1 砍掉“任务队列” (The Queue must die)
*   **动作**: 删除 `task_queue` 及其所有相关代码 (`pushTask`, `processTasks`)。
*   **替代方案**: **自然语言驱动**。
    *   以前：后端检测新角色 -> 推送 `init` 任务 -> EJS 渲染 JSON 模板。
    *   以后：在世界书里写死一条规则：“当新角色出现时，请按照标准格式输出其档案。”
    *   **理由**: LLM 本身就很聪明，不需要我们用代码手把手教它“现在该初始化了”。相信 LLM 的判断力。

### 2.2 砍掉“后端逻辑闭环”
*   **动作**: 后端脚本 (`updaters/*.ts`) 不再主动修改游戏状态（除了时间推移这种纯数学计算）。
*   **替代方案**: **LLM 全权负责**。
    *   以前：用户买东西 -> 前端改变量 -> 后端算钱 -> 后端写回。
    *   以后：用户点击购买 -> 前端发送系统消息 `/send [系统指令：玩家试图购买物品A，请处理交易逻辑]` -> LLM 看到消息 -> LLM 计算并输出 JSON 更新金币和背包。
    *   **理由**: 既然是 AI 游戏，就让 AI 去算。不要在脚本里写复杂的业务逻辑。

### 2.3 改造 EJS 为“纯展示层”
*   **动作**: 删除 `任务执行器.ejs`。
*   **保留**: `变量列表.ejs`。
*   **修改**: `变量列表.ejs` 只负责把 `stat_data` 格式化成好看的文本喂给 LLM。它不再做任何判断，不再产生任何 Side Effects。

### 2.4 放宽 Schema (Zod)
*   **动作**: 将所有字段设为 `optional` 或提供极其宽容的 `default`。
*   **理由**: 只要数据能显示在 UI 上就行。不要因为一个字段填错了就报错。甚至可以接受 LLM 瞎填，反正玩家能在 UI 上看到，如果不爽，玩家可以用 slash command 改回来。

---

## 3. 新的工作流：回归本源

在这个新架构下，流程变得极度简单：

1.  **UI (前端)**:
    *   展示 MVU 变量（血条、金币）。
    *   提供按钮。点击按钮 = 发送一段 `/sys` 指令给 LLM。
2.  **LLM**:
    *   看到上下文（变量列表）。
    *   看到指令（用户说要买东西）。
    *   **自己思考**，输出剧情，输出 `<JSONPatch>` 更新变量。
3.  **MVU (插件)**:
    *   解析 Patch，更新变量。
4.  **Backend (脚本)**:
    *   监听更新，刷新 UI。**仅此而已。**
