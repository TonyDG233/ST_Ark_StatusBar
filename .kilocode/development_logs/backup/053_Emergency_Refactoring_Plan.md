# 053_重构方案_融合与简化 (Refactoring: Fusion & Simplification)

**日期**: 2026-01-29
**状态**: **待批准**
**背景**: 用户对当前架构感到绝望，认为不如现有的纯文本规则模板（粥粥数据库）。

---

## 1. 核心反思：为什么“粥粥模板”更稳定？

我仔细研读了 `粥粥数据库导入模板.json`。它的核心优势在于：
1.  **无代码依赖**: 所有逻辑（`initNode`, `updateNode`）都是**自然语言指令**。LLM 读了就懂，懂了就做。
2.  **所见即所得**: 它是表格，LLM 只需要填空。
3.  **容错率高**: 就算LLM填错了一个格，整个系统不会崩溃。

而我们之前的架构（Backend Queue）试图用**代码**去微操一个**概率性的LLM**，这不仅增加了复杂度，还引入了无数的时序Bug。

**结论**：我们不需要“重新发明轮子”，我们需要**给轮子装上马达**。
*   “粥粥模板”是优秀的轮子（内容、逻辑）。
*   我们的“Custom UI”是马达（交互、可视化）。
*   之前的“Backend Script”是多余的、复杂的变速箱——**拆掉它**。

---

## 2. 新架构：MVU + 粥粥逻辑 (The Hybrid Model)

我们要保留您的核心优势（UI交互），同时吸收“粥粥模板”的稳定性（自然语言驱动）。

### 2.1 数据层：全盘吸收，结构化存储
*   **动作**: 废弃原本过于简略的 Schema，参考“粥粥模板”的详尽列定义（如“感染状况”的详细格式、“战力分级”的描述标准），将其转化为 **Zod Schema**。
*   **目的**: 让数据内容达到同等丰富度，但保持 JSON 格式，以便 UI 读取。

### 2.2 逻辑层：自然语言驱动 (Natural Language Driven)
*   **动作**: **彻底删除** `src/ARK_STATUSBAR/logic/updaters/` 下的所有任务调度代码。
*   **替代**: 将“粥粥模板”中的 `updateNode` 和 `initNode` 逻辑，直接翻译进 `[mvu_update]变量更新规则.ejs`。
    *   *例子*: 不要在代码里写 `if (newChar) pushTask()`。
    *   *直接在Prompt写*: “当有重要新角色登场时，请在 `characters` 对象中插入新条目，必须包含以下字段...”

### 2.3 执行层：去中心化
*   **动作**: 废弃 `task_queue`。
*   **逻辑**:
    *   **初始化**: LLM 看到开局，根据 Prompt 里的 `initNode` 规则，自动输出 JSON Patch 初始化变量。
    *   **更新**: LLM 看到剧情发展，根据 Prompt 里的 `updateNode` 规则，自动输出 JSON Patch 更新状态。
    *   **总结**: LLM 看到 `round_buffer` 满了（Prompt 里写明：当记录超过10条时），自动执行总结并清空。

---

## 3. 您的收益

1.  **开发量暴减**: 不需要写复杂的 TS 逻辑代码，只需要写 Prompt（复制粘贴+改写）。
2.  **稳定性暴增**: 只要 LLM 能听懂话，系统就能跑。没有代码报错，没有竞态条件。
3.  **UI 依然存在**: 因为底层还是 MVU (JSON)，您的 Vue UI 依然可以读取数据，显示血条、背包、立绘。这是“粥粥模板”做不到的。

---

## 4. 执行计划 (Action Plan)

如果您同意这个方向，我们将进行一次“外科手术”：

1.  **Schema 升级**: 将 `src/ARK_STATUSBAR/mvu/schemas/` 扩充，纳入“粥粥模板”的丰富字段。
2.  **逻辑迁移**: 将所有逻辑从 `.ts` 搬运到 `.ejs` (Prompt) 中。
3.  **代码清理**: 删除 `logic/updaters` 目录。
4.  **UI 对接**: 确保前端能正确读取新的 Schema。

**这是挽救项目的唯一可行路径。** 我们停止与环境对抗，顺应 LLM 的特性，用最简单的架构实现最复杂的功能。
