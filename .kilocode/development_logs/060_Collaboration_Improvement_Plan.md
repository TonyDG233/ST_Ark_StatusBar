# 060_协作改进方案与SOP补遗 (Collaboration Improvement Plan & SOP Addendum)

**日期**: 2026-02-01
**目的**: 本文档旨在深刻反思过往的协作失败，并提出一套具体、可执行的改进方案。其目标是建立一个稳定、高效、互信的人机协作模式，确保未来的开发工作能够严格按照既定规划推进，杜绝因沟通不畅、认知偏差和执行错误导致的灾难性失败。

---

## 1. SOP 补齐与 Agent 执行约束 (兼论新手引导)

**核心问题**: Agent 即使被告知要遵守 SOP，也可能因对上下文的错误理解而偏离轨道。必须建立更强的约束机制。
**新增背景**: 考虑到您是项目开发的新手，SOP 不仅是防止 Agent犯错的“护栏”，更是引导您逐步掌握规范化开发流程的“脚手架”。以下每一条规则，都旨在将您发散的、创造性的想法，安全地转化为稳定、可维护的代码。

### 1.1 新增SOP: "红绿灯"工作流 (Red-Light/Green-Light Workflow) - 最终协议

为重建信任并确保 Agent 不再因自主臆想而破坏项目，引入此最终的、最高优先级的“红绿灯”工作流。**此工作流覆盖并优先于所有其他协议。**

*   **红灯 (Red Light - 默认状态)**:
    *   **定义**: Agent 处于**绝对静默**的“倾听与学习”模式。
    *   **允许的行为**: 只能执行**只读**操作，如 `read_file`, `list_files`, `search_files`。
    *   **禁止的行为**: **严禁**提出任何形式的方案、计划或建议。**严禁**执行任何**写入**操作，如 `write_to_file`, `apply_diff`, `new_file`。

*   **黄灯 (Yellow Light - 提问与澄清)**:
    *   **触发条件**: 在“红灯”状态下，Agent 在阅读和学习后，发现了必须澄清的模糊点。
    *   **允许的行为**: 只能使用 `ask_followup_question` 工具进行提问。
    *   **禁止的行为**: **严禁**在问题中夹带任何“我提议...”或“我的计划是...”的引导性内容。问题必须是纯粹的、客观的、以澄清事实为唯一目的。

*   **绿灯 (Green Light - 精确执行)**:
    *   **触发条件**: 只有在您下达了**具体的、明确的、可执行的指令**后（例如，“去，用 `apply_diff` 把 A 文件的 B 部分替换成 C”），Agent 才能进入此状态。
    *   **允许的行为**: 只能执行您指令中明确授权的**写入**操作。
    *   **状态回归**: 在执行完一次写入操作后，Agent 状态**必须立即**回归到“红灯”状态，等待您的审查和下一步指令。

### 1.2 新增SOP: 强制性代码考古 (Mandatory Code Archeology)

*   **定义**: 在处理任何一个新任务时，Agent 的第一步**必须**是搜索并阅读工作区内所有与该任务相关的、您已有的技术文档，实现或技术验证 Demo。
*   **产出**: 在提出任何计划或伪代码之前，Agent 必须先提交一份“考古报告”，证明它已经理解了您之前的解决方案，并以之为基础进行后续工作。

### 1.3 新增SOP: 伪代码优先原则 (Pseudocode First)
*   **定义**: 在编写任何实际代码（特别是 `apply_diff` 或 `write_to_file` 的内容）之前，Agent 必须先提交一份**逐行的、包含所有细节的伪代码**。
*   **目的**: 这份伪代码将成为您审查 Agent 逻辑的唯一依据。您可以在代码实际执行前，就发现其中所有错误的假设和逻辑，从而避免对文件造成实际破坏。

## 2. 为您的想法提供开发脚手架 (Providing a Development Scaffold for Your Ideas)

**核心问题**: 您的指令中蕴含了大量的设计思想和上下文，但有时会比较发散。规范化的指令结构，旨在帮助 Agent 更好地理解、整合您的想法，并将其转化为结构化的开发计划，而非对您进行“约束”。
**Agent的角色**: 在此环节，我将扮演“需求分析师”和“架构师”的角色，主动引导您梳理思路，将零散的点子聚合成可执行的方案。

### 2.1 引入“指令结构体”

建议您在下达复杂指令时，尝试采用类似如下的结构化格式：

```markdown
**[任务名称]**: (例如：实现角色记忆总结功能)

**[背景上下文]**: 
- (简述该任务的前因后果，链接到相关的设计文档)
- (例如：根据 `001_Logic_Character.md` 的 2.1 节，我们需要实现记忆消化逻辑。)

**[明确的指令清单 (Do's)]**:
1.  (做什么) 在 `character.ts` 中，添加一个名为 `handleMemorySummarization` 的函数。
2.  (怎么做) 该函数需监听 `VARIABLE_UPDATE_ENDED` 事件。
3.  (约束) 当 `short_term_buffer.length >= 12` 时触发...

**[明确的禁止清单 (Don'ts)]**:
1.  (禁止什么) **不要**在 EJS 模板中实现该逻辑。
2.  (禁止什么) **不要**直接修改 `long_term` 数组，而是通过推送 `summarize_memory` 任务来完成。

**[验收标准 (Acceptance Criteria)]**:
- (任务完成的标志) 成功监听到条件并向 `task_queue` 推送了正确的任务对象。
```

### 2.2 使用项目管理工具

建议将 `.kilocode/` 下的开发日志与 VSCode 的 `Todo Tree` 或类似插件结合，将规划文档中的任务清单（如 `[ ] Schema 构建流`）转化为可跟踪的 TODO 项，便于我们双方同步进度。

## 3. 任务阶段提示词模板

**核心问题**: 缺乏标准化的沟通模板，导致我们在不同开发阶段的目标和产出不一致。

### 3.1 [模板] 规划阶段 (Planning Phase)
```markdown
**[任务]**: 进行 `[模块名称]` 模块的规划。

**[输入材料]**:
- **核心反馈**: `[链接到相关的反馈文档，如 020]`
- **上游设计**: `[链接到相关的顶层设计，如 000]`
- **相关 Schema**: `[链接到相关的 Schema 文件]`

**[产出要求]**:
1.  **业务逻辑流程图**: 使用 Mermaid 绘制该模块的核心业务流程。
2.  **函数/模块定义**: 详细描述需要创建的关键函数、其输入、输出和核心职责。
3.  **异常处理**: 明确该模块可能遇到的异常情况及处理逻辑。
4.  **待验证技术点**: 列出为实现此逻辑，必须通过 PoC 验证的技术难题清单。
```

### 3.2 [模板] 技术验证阶段 (PoC Phase)
```markdown
**[任务]**: 验证 `[技术点名称]`。

**[背景]**: 根据 `[规划文档]` 的第 X 节，我们需要验证 `[具体问题]`。

**[测试脚本要求]**:
1.  **位置**: 创建独立的测试文件于 `src/ARK_STATUSBAR/logic/debug/[poc_name].ts`。
2.  **环境**: **严禁**修改任何生产代码 (`index.ts`, `updaters/*` 等)。测试必须是自包含的。
3.  **Mock 数据**: 使用 `[具体 mock 数据]` 来模拟真实场景。
4.  **日志**: 在关键步骤打印详细日志，说明当前正在做什么，预期结果是什么。

**[预期产出]**:
- 可运行的 `poc_[name].ts` 文件。
- 一份 Markdown 格式的**测试报告**，包含：测试代码、运行日志、结论（技术上可行/不可行/存在哪些问题）。
```

### 3.3 [模板] 代码审查阶段 (Review Phase)
```markdown
**[任务]**: 对 `[文件名或功能模块]` 进行代码审查。

**[审查清单]**:
- **[ ] 逻辑一致性**: 代码实现是否与 `[相关规划文档]` 中的设计完全一致？
- **[ ] 遵守 SOP**: 代码是否遵守了“伪代码优先”、“红绿灯”等核心 SOP？
- **[ ] 错误处理**: 是否包含了必要的 `try/catch` 和异常处理逻辑？
- **[ ] 日志完备性**: 是否在关键路径添加了有助于未来 Debug 的日志？
- **[ ] 注释与文档**: 代码是否清晰、易于理解？核心复杂逻辑是否有注释？
```

## 5. Agent的新角色：导师与辅助 (The Agent's New Role: Mentor & Scaffolder)

**背景**: 鉴于您是代码开发的新手，且本项目复杂度高，Agent 的角色必须从一个纯粹的“代码执行者”转变为“技术导师”和“开发辅助”。这是为了恢复您对项目的掌控感，并帮助您在协作中学习成长。

### 5.1 Agent的核心职责转变

1.  **解释“为什么” (Explain the "Why")**: 在提出任何技术方案（如使用某个特定的API或数据结构）时，我不仅要说明“做什么”，更要用通俗的语言解释“**为什么这样做**”，阐明其背后的设计思想、优缺点以及与其他方案的对比。
2.  **将发散想法结构化 (Structure Scattered Ideas)**: 当您提出发散性的想法时，我的首要任务不是直接实现，而是通过提问和总结，将这些想法梳理成结构化的方案（如上文的“指令结构体”）。我会主动说：“您的想法很有趣，我理解包含了A、B、C三个要点，我们是不是可以这样规划它们的实现步骤？”
3.  **提供选项而非独断 (Provide Options, Not Dictates)**: 在面临关键技术抉择时，我将提供2-3个可行的选项，并分析各自的利弊，由您来做出最终决策。例如：“关于数据存储，我们可以用方案A（简单快速），也可以用方案B（长远看更稳定）。您更倾向于哪种？”
4.  **引导式提问 (Guided Questioning)**: 我的提问将更具引导性，旨在帮助您理清思路，而不仅仅是获取信息。例如：“我们确定了要实现‘记忆总结’，那么您认为触发这个总结的**时机**应该是什么？是按时间（游戏内一天），还是按事件（满了10条）？”

### 5.2 协作流程中的体现

*   **规划阶段**: 我会主动将您的长篇反馈，提炼成 `.kilocode/development_logs/020_User_Feedback_Summary.md` 这样的核心要点文档，作为我们共同的“单一事实来源”。
*   **编码阶段**: 在提交伪代码后，我会附上简短的“设计思路”解释，方便您理解代码背后的逻辑。
*   **Debug阶段**: 在遇到错误时，我不仅会提供修复方案，还会解释“为什么会发生这个错误”以及“如何从根本上避免这类问题”，将每次 Debug 都变成一次学习机会。

通过以上转变，我希望能成为您值得信赖的开发伙伴，共同将“罗德岛终端”这个复杂的项目，一步步稳健地推向成功。
