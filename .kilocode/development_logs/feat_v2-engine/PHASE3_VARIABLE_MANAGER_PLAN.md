# ARK_GAME 变量管理器架构规划 (Phase 3 Variable Manager)

## 1. 核心职责 (What it does)
这套管理器在服务层（Service Layer）的作用是充当整个剧情引擎的**“数据心脏”**：
- **初始态注入**：在游戏开局时，扫描特定世界书或配置文件，确立当前档的初始变量（如：当前节点ID、好感度、物品栏）。
- **心跳监听与解析**：在每次 AI 回复后（心跳），静默捕获其输出的特殊格式（思维链/更新指令），并解析为结构化数据。
- **守门员与验证器**：绝不信任大模型。所有解析出的数据必须经过强类型校验，过滤掉 AI 的幻觉（如凭空捏造不存在的道具）。
- **时光机**：与酒馆原生的楼层系统解耦或轻度绑定，确保玩家“撤回消息”时，游戏进度能无缝回档。
- **UI 响应源**：作为单一数据源（SSOT），通过自定义事件（CustomEvent）驱动前端界面发生变化，实现文本与视图的彻底分离。

## 2. 核心组件构成 (Components)

我们将系统划分为四个高内聚的模块（基于对外部框架的吸收与精简）：

1. **`StateContainer` (状态容器与 Zod 验证层)**
   - 包含针对方舟剧情的 `zod` Schema（如严格限制节点跳转逻辑、资源数值）。
   - 提供状态更新方法，内部使用 Zod 进行 `coerce` 和 `clamp` 过滤。
2. **`ParserEngine` (增量解析器)**
   - 捕获 AI 输出。可以兼容基础的文本提取与高级的 Function Calling。
3. **`PersistenceService` (持久化与时光机)**
   - 负责将状态落盘。
   - 依赖酒馆的 `replaceVariables(..., {type: 'message'})` 机制实现低成本撤回回溯，但需严格控制保存数据的体积，避免性能雪崩。
4. **`PromptInjector` (上下文与防污染中间件)**
   - 负责把当前的状态转换为精简的字符串交给大模型。
   - **绝对防线**：在发送前把历史聊天记录里丑陋的变量块清洗掉，防止污染 AI 上下文。

## 3. 涉及的技术栈与酒馆 API
- **类型系统**：`zod 4.x`
- **持久化 API**：`@types/function/variables.d.ts` 
- **钩子 API**：`tavern_events.MESSAGE_RECEIVED` 及发包前置拦截器。
- **通信总线**：原生的 `CustomEvent`。

## 4. 实施路线与具体做法 (Implementation Strategy)
*   **Step 1: 确定数据结构 (Data Contract)**
    设计我们的核心数据结构，确立各级变量的边界。
*   **Step 2: 搭建清洗与解析管线**
    利用既有的成熟解析器或直接引入 JSON 解析方案，对接 Zod 清洗流。
*   **Step 3: 改造输入输出流 (The Pipeline)**
    挂载双轨模型调用（可选），在获取增量后触发内部事件完成更新与落盘。
*   **Step 4: 接入前端体系**
    后端逻辑只向外抛出自定义事件，前端 Vue 组件通过 Facade 层获取只读数据进行渲染。

## 5. 潜在风险与应对预案 (Risks & Mitigations)

| 风险点 | 描述 | 应对预案 (Mitigation) |
| :--- | :--- | :--- |
| **1. AI 格式破坏 (Hallucination)** | 免费/本地模型无法稳定输出合法的结构格式，导致解析崩溃。 | 必须保留极强的文本容错提取机制作为兜底，结合 Zod 的强力纠错。 |
| **2. 上下文污染 (Prompt Pollution)** | 记录在聊天中的更新代码被大模型看到，导致后续它不写小说只写代码。 | 必须实现发送前清洗机制（Hook 发送前管线），在请求发出前正则抹除所有代码痕迹。 |
| **3. 性能雪崩 (State Bloat)** | 随着流程变长，记录在每层楼的变量体积线性膨胀，导致读写卡顿。 | 极简主义设计：当前框架**坚决不记录长文本或非必要设定**。全量静态数据必须剥离到静态文件中。 |
