## 1. 核心愿景回顾：从“UI挂件”到“罗德岛终端”

回顾 Phase 2 和 Phase 3 的规划文档（特别是 `005` 和 `021`），项目的核心愿景是非常宏大且逻辑自洽的。

*   **Phase 1** 只是一个简单的开场 UI。
*   **Phase 2** 试图引入 **MVU (Magical Variable Update)**，赋予系统“记忆”和“状态”。
*   **Phase 3** 试图通过 **EJS 动态提示词** 和 **双模型 (Dual-LLM)** 策略，实现一个闭环的“游戏化体验”。

**理想中的工作流**:
1.  **LLM 剧情生成** -> 2. **额外模型解析** -> 3. **MVU 更新变量** -> 4. **后端脚本触发逻辑 (如任务结算、时间流逝)** -> 5. **EJS 渲染新状态** -> 6. **注入下一轮 Prompt**。

这是一个标准的**事件驱动架构 (Event-Driven Architecture)**。

---

## 2. 技术架构深度解析：原本的设计

我们构建了一个极其复杂的精密机器，包含四个咬合的齿轮：

### 2.1 数据层 (The Soul - Schema)
*   **设计**: 使用 `Zod` 定义了极其严格的变量结构 (`Global`, `Player`, `Character`, `Chronicle`)。
*   **现状**: 结构定义本身非常完善，涵盖了从“四维地点”到“分层记忆”的所有细节。
*   **问题**: 过于理想化。它假设数据总是完整的、合法的。当 LLM 输出残缺数据（如缺字段）时，系统往往陷入“校验失败 -> 报错 -> 尝试修复 -> 再次失败”的死循环。

### 2.2 逻辑层 (The Brain - Backend Updaters)
*   **设计**: 位于 `src/ARK_STATUSBAR/logic/updaters/`。监听 `Mvu.events.VARIABLE_UPDATE_ENDED` 事件。
*   **核心逻辑**:
    *   **Global**: 负责时间推进、回合计数。
    *   **Character/Player**: 负责“档案自愈”（检测空值 -> 推送 `repair` 任务）。
    *   **Chronicle**: 负责“任务调度”（检测缓冲区满 -> 推送 `summary` 任务）。
*   **致命缺陷**: **严重依赖事件的时序和稳定性**。
    *   在 SillyTavern 中，`VARIABLE_UPDATE_ENDED` 的触发时机并不像后端服务器那样可靠。它可能在一次生成中触发多次，也可能不触发。
    *   **Race Condition (竞态条件)**: 脚本在变量更新后立即修改变量（如推送任务），这可能导致无限递归更新，或者与 MVU 自身的写入操作冲突。

### 2.3 表现层 (The Mouth - EJS Prompts)
*   **设计**: 位于 `src/ARK_STATUSBAR/prompts/dynamic/`。
*   **核心逻辑**: `变量列表.ejs` 负责展示状态，`[mvu_update]任务执行器.ejs` 负责将后端推送的 JSON 任务翻译成自然语言指令。
*   **异化**: 在开发后期（见 `038_Phase3_EJS_Implementation_Blueprint.md`），为了解决后端脚本“慢一拍”的问题（即脚本更新了任务队列，但 EJS 已经在脚本运行前渲染完了），引入了 **"EJS Hotfix"**。
    *   **这是崩坏的开始**：我们在 EJS 模板里直接写了应该属于后端的业务逻辑（如“开局初始化检测”）。这打破了“数据-逻辑-表现”分离的原则，让 EJS 变得极其臃肿且难以维护。

### 2.4 执行层 (The Hand - Dual LLM)
*   **设计**: 主模型写剧情，额外模型写 JSON Patch。
*   **现状**: 这一部分反而运作得相对正常，但受限于上游指令的混乱（任务队列里堆积了过期的、重复的任务），额外模型经常感到困惑，导致输出格式错误或死循环。

## 3. 为什么会崩溃？——根源分析

项目接近崩溃并非因为代码写得烂，而是因为我们试图在沙地上盖摩天大楼。

### 3.1 战略误判：在不可靠的运行时上构建精密架构
我们把 SillyTavern/TavernHelper 当作了一个标准的、稳定的 Node.js 后端服务器来对待。
*   **现实**: 酒馆的脚本环境是单线程的、事件触发不稳定的、且生命周期受用户操作（刷新、回退、删除消息）严重影响的。
*   **后果**: 我们设计的“精密齿轮”（监听 -> 计算 -> 推送任务 -> EJS渲染）只要有一环卡住（例如事件没触发，或者顺序反了），整个链条就断了。

### 3.2 战术失误：初始化风暴 (Initialization Storm)
在 Phase 3，我们引入了自动化的“档案自愈”和“开局初始化”。
*   **现象**: 开局时，Player 是空的，Characters 是空的。
*   **逻辑**: 后端检测到空 -> 推送 Init 任务 -> EJS 渲染任务 -> LLM 执行初始化 -> 变量更新 -> 后端再次检测...
*   **死结**: 由于通信延迟和 EJS 渲染时机的问题，用户发第一条消息时，EJS 往往还没以此拿到后端推送的任务。导致开局第一轮 LLM 根本不知道要初始化，第二轮才开始，严重破坏体验。
*   **错误修复**: 为了修这个问题，我们在 EJS 里加了 Hotfix（强制在 EJS 里做初始化检测）。这导致逻辑分裂：后端有一套检测逻辑，EJS 里有一套检测逻辑。两者互相打架，导致任务队列里全是重复任务。

### 3.3 复杂度爆炸 (Complexity Overload)
看看 `TaskQueueSchema` (`src/ARK_STATUSBAR/mvu/schemas/global.ts`)：
我们定义了 `init_profile`, `repair_profile`, `summarize_memory`, `ten_round_summary` 等 10 多种任务类型。
每一种任务都需要：
1.  后端检测逻辑 (`updaters/*.ts`)
2.  任务队列管理 (`pushTask`)
3.  EJS 渲染模板 (`任务执行器.ejs`)
4.  LLM 执行指令 (`JSON Patch`)
5.  后端清理逻辑 (`postProcessCompletedTasks`)

维护成本呈指数级上升。改一个字段，要动 5 个地方。对于一个单人/小团队开发的项目，这种复杂度是不可持续的。

## 4. 破局之道：如何挽救？

基于上述分析，继续修 Bug 是没有尽头的。我们需要**做减法**，并实施**防御性开发**。

### 4.1 立即止损：砍掉“自动化闭环”
*   **现状**: 后端检测 -> 推任务 -> LLM 执行 -> 后端清理。这个闭环太长、太脆。
*   **建议**: 
    *   **废弃后端任务队列**。
    *   **回归 EJS 驱动**。将逻辑收敛到 EJS 中。
    *   **例如**: 不需要后端检测“是否需要初始化”。直接在 `任务执行器.ejs` 里写：`<% if (!player.profile.name) { %> [指令：请初始化玩家] <% } %>`。
    *   **优势**: 逻辑和 Prompt 在一起，所见即所得，不存在时序延迟，也不需要复杂的队列管理。

### 4.2 架构降级：从“事件驱动”转为“状态轮询/即时计算”
*   不要监听 `VARIABLE_UPDATE_ENDED` 去做复杂的业务逻辑（如任务结算）。
*   后端脚本只负责**绝对必要**的、LLM 做不到的事情：
    *   **时间/日期格式化**（纯计算）。
    *   **数据清洗**（比如把过长的数组切断，防止爆 Token）。
    *   **UI 同步**（把变量同步给 Pinia）。
*   把“决策权”交还给 LLM 和 EJS。

### 4.3 实施“防御性开发” (SOP 落地)
按照我们新修订的 SOP：
1.  **环境勘探**: 承认我们不知道 `tavern_events` 到底什么时候触发。不要依赖它做关键流程。
2.  **架构防火墙**:
    *   在 EJS 中加入大量的防御性代码（`try-catch`，空值检查）。
    *   在 Schema 中把所有字段设为 `optional` 或提供 `default`，**永远不要让 Zod 校验失败导致流程崩溃**。校验失败就用默认值，让游戏继续下去。

---

## 5. 总结

您感觉到“接近崩溃”是非常正常的。因为我们试图用一套**极度严苛的工程标准**（Zod 强校验 + 复杂的异步状态机）去约束一个**本质上是模糊和概率性**的 LLM 系统。

**下一步行动建议**:
不要再往 `logic/updaters/` 里加代码了。
开始**拆除**复杂的任务队列系统。
将核心逻辑（初始化、修复、总结）直接硬编码到 EJS 模板中。
让代码为剧情服务，而不是让剧情被代码困死。
